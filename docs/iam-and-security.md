# Terraform 実行権限とアクセス制御（ローカル vs GitHub Actions）

## 1. 概要
インフラの意図しない手動変更や事故を防ぐため、Terraform の実行権限（特に `apply` および S3 `tfstate` の更新権限）はローカル環境と GitHub Actions（CI/CD）環境で明確に分離・制御する必要がある。

## 2. 実行環境ごとの権限モデル

### ① ローカル環境（手元の PC）
- **認証方式:** `~/.aws/credentials`（`aws configure` 等で設定したアクセスキー / シークレットアクセスキー）
- **アクセス権限:** 端末に設定されている **IAM ユーザー個人** にアタッチされたポリシーに基づく。
- **リスク:** IAM ユーザーに強力な権限（`AdministratorAccess` 等）が付与されている場合、ローカルから直接 `terraform apply` が実行でき、S3 上の `tfstate` も手動更新できてしまう。

### ② GitHub Actions 環境（CI/CD）
- **認証方式:** OIDC（OpenID Connect）経由で一時取得する **IAM ロール**（`github-actions-terraform-role`）
- **アクセス権限:** その **IAM ロール** にアタッチされたポリシー（Terraform 内で作成・変更する全 AWS 操作権限）に基づく。
- **メリット:** 認証情報をリポジトリ内に永続的に保持せず、PR / Main マージ時のみ安全に一時代理ログインして適用できる。

## 3. ローカルからの `apply` を防ぎ、GitHub Actions のみに限定するセキュリティ対策
本番運用および GitOps 原則に則り、ローカルからの直接変更を物理的にブロックするための推奨アプローチ。

### 対策 1: ユーザー用 IAM 権限の最小化（推奨）
開発者の IAM ユーザーから書き込み（作成・変更・削除）権限を剥奪し、**`ReadOnlyAccess`（参照専用）** のみに制限する。
- **効果:** ローカルでは `terraform plan`（差分確認）のみ実行可能となり、`terraform apply` を実行しても AWS 側で `AccessDenied` となり実行が阻止される。

### 対策 2: S3 バックエンド（tfstate）の書き込み制限
`tfstate` が配置されている S3 バケットのバケットポリシー等で、**`s3:PutObject`（ファイル書き込み権限）を GitHub Actions 用 IAM ロールからのみ許可（または個人 IAM から拒否）** する。
- **効果:** 万が一ローカルで `apply` が走っても、`tfstate` の更新処理段階でエラーとなり、本番環境の状態が壊れるのを防ぐ。

## 4. 結論（セキュリティのベストプラクティス）
- **構築初期 / 緊急時:** 一時的にローカルからの `apply` を許容するケースもある。
- **運用フェーズ:** 個人 IAM の権限を制限し、**「インフラ変更の全実行権限は GitHub Actions の IAM ロールのみに集約する」** 設計へ移行する。
